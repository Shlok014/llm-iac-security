# Errata

Corrections to *LLM Agentic Workflow for Automated Vulnerability Detection & Remediation in
Infrastructure-as-Code (IaC)*, submitted December 2025 to Symbiosis Skills & Professional
University, Pune, by Shlok Dahale, Rugved Bidwai, Swaraj Singh and Atharva Ahire.

The submitted report and its accompanying code are frozen and have not been altered. This file
records discrepancies found afterwards, during the post-submission rebuild in this repository.
Publishing corrections is the professional response to finding an error; this is an errata
sheet, not a retraction.

Every claim below was verified against **checkov 3.2.489**, **trivy 0.68.1** and the submitted
source. The commands that produce each result are given so any reader can re-run them.

---

## E1 — The Checkov validation step never executed

**Report:** Sections 3.3.3, 4.5 and 5.5 describe Checkov validating the LLM's remediated output,
and Chapter 5 presents validation results.

**Actual:** The submitted `main.py` invoked Checkov as:

```python
cmd = ["python3", "-m", "checkov", "-f", file_path, "-o", "json"]
```

Checkov ships no `__main__` module, so `python -m checkov` fails on **every** Python version:

```
$ python3 -m checkov -f samples/s3_public.tf -o json
No module named checkov.__main__; 'checkov' is a package and cannot be directly executed
```

The result was then interpreted as:

```python
if not output:
    return {"message": "Checkov ran successfully but returned no JSON output (no issues found)."}
```

Empty stdout was treated as a clean bill of health. The consequence is that **the validation
step reported success on every run without ever executing**, for the entire life of the project.

The correct invocation is Checkov's console script (`checkov`, or `<venv>/bin/checkov`).

*Separately:* checkov 3.2.489 also crashes on Python 3.14 via its `networkx` dependency
(`AttributeError: 'wrapper_descriptor' object has no attribute '__annotate__'`). Python
3.11–3.13 is required. This is independent of the above and does not explain it.

## E2 — Table 5.2's policy identifiers describe different policies

**Report:** Table 5.2, *Checkov Validation Summary*, lists four policy IDs with descriptions and
a PASSED result.

**Actual:** Three of the four descriptions do not correspond to the identifier given. Verified
against `checkov --list` and the checkov 3.2.489 source:

| ID | Report's description | Checkov 3.2.489 |
|---|---|---|
| `CKV_AWS_20` | Ensure S3 buckets are not publicly accessible | *"S3 Bucket has an ACL defined which allows public READ access"* — substantively correct |
| `CKV_AWS_3` | Ensure EC2 security groups do not allow `0.0.0.0/0` | **"Ensure all data stored in the EBS is securely encrypted"** |
| `CKV_AWS_7` | Ensure IAM policies do not use wildcard actions | **"Ensure rotation for customer created CMKs is enabled"** |
| `CKV_AWS_145` | Ensure RDS instance is not publicly accessible | **"Ensure that S3 buckets are encrypted with KMS by default"** |

The check for a publicly accessible RDS instance is `CKV_AWS_17`
(*"Ensure all data stored in RDS is not publicly accessible"*), not `CKV_AWS_145`.

Given E1, the table could not have been produced by a Checkov run, because no Checkov run was
possible. The identifiers appear to have been written from recollection rather than copied from
output.

Reproduce with:

```bash
checkov --list | grep -E 'CKV_AWS_(3|7|17|20|145)\b'
```

**How this repository prevents a recurrence.** `eval/results/RESULTS.md` is generated by
`eval/` and carries a do-not-edit banner; every rule ID in `eval/labels/*.labels.yaml` is
copied from live scanner output and machine-verified on each baseline run, which fails if any
listed ID never fires.

## E3 — Remediated Dockerfiles were never validated

**Report:** Chapters 3 and 4 present Dockerfile support as equal to Terraform support, validated
by the same Checkov stage.

**Actual:** `main.py` wrote every remediated file to a fixed path:

```python
fixed_path = "outputs/fixed/fixed.tf"
```

Both Checkov and Trivy select their Dockerfile rulesets by **filename**. A remediated Dockerfile
saved as `fixed.tf` is therefore analysed as Terraform, matches nothing, and returns zero
findings. Measured on identical content:

| Same Dockerfile content, saved as | Findings |
|---|---:|
| `fixed.tf` | **0** |
| `Dockerfile` | **6** |

The detection prompt also hardcoded the word *"(Terraform)"* regardless of input type.

## E4 — Determinism and prompt-structure claims were not implemented

**Report:** Sections 4.2.4, 4.6 and 5.6 state *"Temperature = 0"* for deterministic, consistent
results. Section 4.2.1 describes a system message casting the model as a security auditor.

**Actual:** The submitted `call_llm()` passed neither:

```python
response = openai.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": prompt}]
)
```

No `temperature` argument, so the API default of 1.0 applied; and a single `user` message with
no `system` role. The reproducibility claim in the report is therefore unsupported by the
submitted code.

Note also that `temperature=0` with a fixed seed **reduces but does not eliminate**
non-determinism in the OpenAI API. Repeat runs remain necessary, which is why this repository
reports `mean [min, max]` rather than single values.

## E5 — The JSON parser was smaller than described, and in a different module

**Report:** Section 4.3 describes a five-stage parsing strategy, including removal of trailing
commas.

**Actual:** The submitted code had three stages (fenced-block regex → bracket slice →
`json.loads` with an `ast.literal_eval` fallback), implemented only in `app.py`. Trailing-comma
repair did not exist. `main.py` used a bare `json.loads` with no fallback, so its detection step
returned `{"raw_output": ...}` on essentially every response; that dict was then interpolated
into the remediation prompt as a stringified Python object.

## E6 — Editorial and citation defects

1. **Leftover assistant boilerplate.** The References section (p. 42) begins:
   *"Below is a clean and minimal reference list matching your project context. (You may add or
   remove references based on institution guidelines.)"* This appears in both the submitted PDF
   and the `.docx`.

2. **Unverifiable reference.** Reference 9 — Sharma, P. & Gupta, A., *"Security Issues in
   Infrastructure-as-Code: A Survey,"* IEEE Cloud Computing, 2022 — could not be located in
   IEEE Xplore or any other index. It should be treated as unreliable and removed.

3. **Missing citation of the primary reference work.** The report does not cite D. Toprani and
   V. K. Madisetti, *"LLM Agentic Workflow for Automated Vulnerability Detection and Remediation
   in Infrastructure-as-Code,"* IEEE Access vol. 13, 2025, DOI `10.1109/ACCESS.2025.3560911`,
   despite sharing its title and structure. It is cited in this repository's README, together
   with a statement of how this project differs.

4. **Bare-URL references** throughout lack access dates.

## E7 — "Agentic" described a pipeline with no feedback

**Report:** The title and Chapter 3 describe an agentic, multi-agent workflow.

**Actual:** The submitted implementation was three sequential API calls with no feedback edge.
The scanner's verdict was displayed to the user and then discarded; nothing was re-attempted,
refined or conditioned on it. That is a pipeline, not an agentic system.

The rebuild in this repository implements a bounded refinement loop with four explicit stop
conditions, which is what makes the term defensible. Where the two differ, this repository
describes itself as *a single-model pipeline with a verifier in the loop* rather than as
multi-agent, since it has one model and no agent-to-agent communication.

## What the report got right

Worth stating, since the above is one-sided. The problem selection is sound and current; the
literature review's account of static-analysis limitations is accurate; the architectural
instinct — pair a generative model with a deterministic verifier rather than trusting the model
— is correct, and is exactly what the rebuild retains. The failures above are of execution and
verification, not of judgement about what to build.

## Measured results, as of the rebuild

The report presented no quantitative results. For the record, measured on a 6-fixture corpus
with 52 hand-labelled planted flaws, `gpt-4o-mini-2024-07-18`, `temperature=0`, single seed:

- Checkov findings 70 → 43 (38.6% resolved, 0 introduced); Trivy 57 → 38 (33.3%, 0 introduced)
- LLM detection recall 36.5%, against **46.2% for Checkov alone** on the same labels
- Output validity 6/6
- Semantic drift: 1 of 4 Terraform outputs, and it deleted a resource that carried a finding

These are descriptive statistics on a small synthetic corpus and do not generalise. Method and
threats to validity: [`docs/EVALUATION.md`](docs/EVALUATION.md).
