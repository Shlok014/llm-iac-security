# The corpus

⚠️ **Everything outside `secure/` is deliberately insecure.** These are scanner fixtures, not
templates. Do not deploy them. Every credential in them is a fake placeholder
(`AKIA_FAKE_KEY`, `Password123!`) and none has ever been valid. Automated secret scanners will
flag this directory; that is expected. See [`../SECURITY.md`](../SECURITY.md).

Ground truth for each fixture lives in [`../eval/labels/`](../eval/labels/), one YAML file per
fixture. Every scanner rule ID in those files is checked against live scanner output by
`tests/test_labels_integrity.py` — a rule ID that does not fire fails the build.

Regenerate with `make baseline` — but read the warning it prints first.

**The two totals do not sum to anything meaningful.** Checkov's 140 and Trivy's 111 count *rule
violations*; one planted flaw trips many rules, and the two rulesets overlap heavily. The
recall denominator is the label column.

**34 of the 91 planted flaws are invisible to both scanners.** That gap is the only defensible
basis for claiming an LLM adds anything over two tools that run in a second and cost nothing.
It is concentrated in the Dockerfiles, where things like `curl … | sh`, copying secrets into an
image layer, and running `sshd` inside a container have no corresponding policy.

## Two generations of fixture, and why it matters

The original six (`vulnerable_main.tf`, `vulnerable_network.tf`, `ec2_open.tf`, `s3_public.tf`,
`vulnerable.Dockerfile`, `docker_insecure.Dockerfile`) **annotate their own planted flaws** in
comments:

```hcl
acl = "public-read"        # <- public-read is insecure
```

That contaminates any detection score measured on them — the model can read the answer key
rather than the code. It was measured at **13.5 points of recall**, roughly a quarter of the
model's apparent ability. The workaround is `eval/corpus/stripped/`, generated by
`eval/strip_comments.py` and verified by the invariant that scanner counts must be identical
before and after stripping.

The six added later (`vulnerable_lambda.tf`, `vulnerable_eks.tf`, `vulnerable_kms_logging.tf`,
`vulnerable_apigw_sns.tf`, `node_insecure.Dockerfile`, `java_insecure.Dockerfile`) carry **no
flaw-naming comments and no give-away resource names** — `aws_kms_key.billing_exports`, not
`insecure_key`. They are uncontaminated by construction rather than by post-processing, which
is the stronger property: stripping removes comments, but it cannot remove a hint encoded in an
identifier.

They also cover services the original set never touched. The originals are S3, EC2, RDS, IAM
and VPC only; the additions bring Lambda, EKS/ECS/ECR, KMS/CloudTrail/CloudWatch, and API
Gateway/SNS/SQS.

## `secure/` — the negative controls

Four files that are genuinely secure and score **zero findings** from both scanners (134
passing checks between them). Without clean input there is no way to measure false alarms on
correct infrastructure, and *"does it cry wolf?"* is a fair question to ask a security tool.

Their label files carry `labels: []` deliberately. An empty label set is a claim, not a stub:
**any finding reported on these files is a false positive.**

Unlike the rest of this directory, these are reasonable to read as examples — though still not
to deploy without review, since they are illustrative rather than complete.

## Adding a fixture

1. Write it with no comment naming a flaw and no give-away resource names.
2. Run both scanners and copy the real rule IDs — never write an ID from memory. That mistake
   is what [`../ERRATA.md`](../ERRATA.md) E2 documents, and it is why the integrity test exists.
3. Write `eval/labels/<stem>.labels.yaml`. Mark `detectable_by_scanner: false` only after
   confirming *neither* scanner reports the flaw; that subset carries the project's central
   claim, so it has to be trustworthy.
4. `pytest tests/test_labels_integrity.py -m slow` must pass.
